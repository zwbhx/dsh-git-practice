# 分支与提交约定（v0.1.0）

> 本文件是本仓库的「团队约定」最小版，个人项目也照此执行，目的是让 3 个月后的自己看得懂。

## 1. 提交信息：Conventional Commits

```
<type>(<scope>)!: <subject>

<正文：为什么改，而不是改了什么>
<空行>
BREAKING CHANGE: 破坏性变更说明（可选）
Closes #12
```

### type 白名单（11 个）

| type | 用途 | 会不会进 CHANGELOG |
|---|---|---|
| `feat` | 新功能 | 会（Features） |
| `fix` | 修 bug | 会（Bug Fixes） |
| `docs` | 只改文档 | 会（Documentation） |
| `style` | 空格/分号/格式化，不改逻辑 | 不会 |
| `refactor` | 重构，不改行为 | 会（Refactor） |
| `perf` | 性能优化 | 会（Performance） |
| `test` | 增删测试 | 不会 |
| `build` | 构建系统/依赖 | 会（Build） |
| `ci` | CI 配置与脚本 | 会（CI） |
| `chore` | 杂项（版本号、忽略规则） | 不会 |
| `revert` | 回滚某次提交 | 会（Revert） |

### scope

- 可选。本仓用 `cli`、`lint`、`docs`、`ci` 四个。
- 必须 kebab-case：`weekly-checklist` ✅，`Weekly Checklist` ❌。
- **无 scope 的提交是合法的**，`docs: 补充约定` 完全正确（这是 v0.1.0 review 抓出来的 bug，见 `PR演练记录.md` R1）。

### subject

- 不超过 50 字，不以句号结尾，动词开头（中文写「新增/修复/移除/补充」）。
- 一次提交只做一件事；「顺手改的」另开一个提交。

## 2. 分支

| 分支 | 从哪来 | 合到哪 | 命名 |
|---|---|---|---|
| `main` | — | — | 固定 |
| 功能 | `main` | `main` | `feat/<短横线描述>` |
| 修复 | `main` | `main` | `fix/<短横线描述>` |
| 文档 | `main` | `main` | `docs/<短横线描述>` |
| 杂项 | `main` | `main` | `chore/<短横线描述>` |

- 合并用 `git merge --no-ff`（保留「这里曾经有一条分支」的证据），团队有 squash 约定时按团队来。
- 合并后立刻删分支：`git branch -d <name>`。
- 分支存活超过 2 周 = 该拆了。

## 3. 版本与 tag

- 语义化版本 `vMAJOR.MINOR.PATCH`：破坏性 → MAJOR，新功能 → MINOR，修复 → PATCH。
- 打**附注标签**（annotated）：`git tag -a v0.1.0 -m "..."`，不要用轻量标签。
- 每次 tag 必须同步更新 `CHANGELOG.md`，commit 用 `docs(changelog): ...`。

## 4. 推送前自查（30 秒）

```bash
git status                    # 有没有忘记 add 的文件
git diff --cached             # 逐行看这次到底提交了什么
git diff --cached | grep -iE 'api[_-]?key|token|password|secret|BEGIN .*PRIVATE KEY'
git log --oneline -5          # 信息是否符合规范
```

命中任何一行 → 停下来。密钥一旦推上去，改历史也不等于没泄露，要立即吊销。

## 5. CI 会跑什么

`.github/workflows/ci.yml` 三步：语法编译（`compileall`）→ unittest → 对最近一次提交信息跑 `commit_lint.py`。
本地等价命令：

```bash
python -m compileall -q scripts
python -m unittest discover -s tests -v
python scripts/commit_lint.py "$(git log -1 --pretty=%s)"
```
